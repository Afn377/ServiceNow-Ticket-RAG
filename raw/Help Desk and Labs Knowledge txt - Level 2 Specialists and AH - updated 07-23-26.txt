The NB-ITS Help Desk closes at 4:30 pm Monday-Friday and is closed on weekends. Users who call the NB-ITS Help Desk after it has closed will be presented with the option to speak to an NB HD After-Hours consultant. This article will provide you with guidance on how to handle some common ITS issues. If you cannot assist the user, please let the user know that you will be moving their ticket, and an ITS specialist will assist them during regular business hours. If the user indicates their issue is an emergency, please use the FT on-call list. If you are unsure if the user is supported by ITS know that ITS supports most users who land in the Echo domain on Connect.
Incidents that need to be handed off to the NB ITS Help Desk should be placed in the ESD - Information Technology Services (ITS) assignment group. 
Unlocking ITS Account
If a user's ITS account is locked, you must reassign the incident to the ESD - Information Technology Services (ITS) assignment group. After-hours staff cannot unlock ITS accounts.
Creating/Recreating New ITS User Account
If a user needs to create a new ITS user account, you can get them started on the process by doing the following:
•	Verify if the user is a Full Time Staff member or a student worker.
•	Provide the following link to the user:
o	Full-Time staff: https://its.rutgers.edu/services/its-account-creation-and-reactivation-regular-staff
o	Student worker: https://its.rutgers.edu/services/its-account-creation-and-reactivation-student-staff
•	The user will be asked to log in
•	Select the link for the request form
•	The form will generate a sys admin ticket for ITS staff to follow up on
•	At this point,t you can notify the user that the ITS Help Desk will be reaching out to them to schedule a new user orientation 
New User Orientation
If a user asks to schedule a new user orientation, you will need to reassign the incident to the ESD - Information Technology Services (ITS) assignment group.
If a user asks what is part of a new user orientation you can provide the following information:
•	Set up Outlook, also inform them of connect.rutgers.edu.
•	Change Default PDF user to Adobe Reader (or Acrobat if their computer has it).
•	Take note of programs on the desktop, if they don’t need something you can get rid of it and remove the label off KACE, if they need a piece of software they don’t have, start the process of getting it. 
•	Change the Default Mail program to Outlook.
•	Change the default browser to their desired default.  
•	Show users the Snipping Tool. This will help capture error messages when they want to talk to the Help Desk. 
•	Make user aware they should not Shut Down ever. We do updates at night, and we must keep their computers updated with security patches. 
•	Show them how to log off/lock the computer instead. 
•	Teach them how to interact with the help desk.
•	Point out the stickers on their monitor, the contact info, and the computer name. 
•	Explain its a good idea to reboot first before calling with a support issue.
•	If emailing, include call back number, department, computer name, and suitable time to call back.  
•	Set them up with remote desktop and VPN instructions if they need them. This can be found on its.rutgers.edu/documentation.
•	Do the same for email on the phone. 
•	Show them the shortcut to the ITS website that is on their desktop.

Alert Status Types
For planned maintenance
If there is a planned maintenance, one of the following alert statuses (depending on the alert description) should be used:
•	Scheduled ¬– For the initial alert of any planned maintenance.
•	Update – As an alert status if any updates need to be shared that occur before or during the planned maintenance.
•	Completed – Once the maintenance is done, this status should be chosen, and alert description should be drafted saying that the planned maintenance has been completed.
For service issue
If an issue with a service occurs, one of the following alert statuses (depending on the alert description) should be used:
•	Investigating/Identified – For the initial alert of any planned maintenance.
•	Update ¬– As an alert status if any updates need to be shared before the service issue is resolved.
•	Resolved – Once the service issue has been resolved, this status should be chosen, and an alert description should be drafted indicating that the planned maintenance has been completed.

" KB0014876 IT Help Desk - Application Support General - Timeline Reporting "
Timelines are a critical part of Applications Support and they are required once you begin to escalate an issue. Timelines are a way for all involved parties to keep track of an issue, and provide accurate information to customers. This is why it is important to create running and final timelines for all escalated issues. 
Final Timelines should always CC operator@oit.rutgers.edu and hd_mgr@oit.rutgers.edu as well as any other applicable parties. Applicable parties are customers (not users) involved in the issue. Typically, those you have escalated the issue to would be CC'd in a timeline. Additionally, the incident created for the issue and the End of Shift (EoS) report for that time period should have a copy of the timeline in it as well.
In addition to a final timeline, you should also send a working timeline to operator@oit.rutgers.edu and hd_mgr@oit.rutgers.edu as well as any other applicable parties. A working timeline should be sent after an issue has been escalated but before it is resolved. For example, if you call a contact and they state that they will look into it and call you back, you can send a working timeline.

Environment - Power Outage Checklist for After Hours
Please read thoroughly and ask/call a supervisor at any time if you have any questions on what to do.
•	This form must be submitted to a manager after the outage is resolved via print out or email. Whichever is quicker at the time.
•	This form can be printed using the printer in the old apps office. The computers in the NOC have access to the Color LaserJet Pro MFP M281fdw.
•	All calls and texts should be made from the AH iPhone, unless there is an issue reported with the phone.
There are three scenarios that may happen with a power outage. Your first indication of an outage is that the lights will flicker. This could lead to the following scenarios: 
1.	Generator turns on: The UPS (uninterruptible power supply) carries the data center load to give time for the generator to turn on. Once the generator turns on you will receive an automated email from omx@omnimetrix.net that the generator is running. The majority of the building is now powered by the generator, though wall outlets in offices and some lights will be not work when on generator power, for example the bathrooms by the old apps office.
2.	Generator does NOT turn on: The UPS switches to battery power, but the generator does not turn on. We will not get an email from omx@omnimetrix.net, but we will get emails "On Battery" from the UPS, and a variety of alerts from the data center monitoring software. 
1.	The UPS batteries will carry the data center load for ~20 minutes and the UPS will send email indicating how much battery life remains. Once the batteries are exhausted everything will go dark because we will have lost all power. It's important to know that the data center air conditioners will only run under generator power, so the room will begin to get very hot. Also, the hallway lights and elevators will not function.
3.	Glitch: The lights flicker, but the generator does not turn on. We do not get an email from omx@omnimetrix.net and we do not lose power after 1 minute. This means there was only a glitch and we have returned to normal power. You can also check if all the lights are on in the basement of Hill Center.

Knowledge Article Basics
Article States
Articles are categorized in one of the following States in the Workflow field. 
Draft
Indicates it is in edit mode and the settings/article body can be changed. This occurs when you first create a new article or when you Checkout an existing article to make changes to it. The version number of the article will show with a decimal after it to indicate it is not published (ex: Version 0.01 for a new article)
Review
When a Draft is ready, clicking Publish puts the article in the Review state. The appropriate owners of the Knowledge Base the article is in would then need to approve it before it is visible to users. 
Scheduled for Publish
For articles that have been approved after being reviewed but have a Scheduled Publish Date set for the article that has not passed yet. 
Published
The article is visible to users based on it’s Can read and Cannot read settings. Published articles have version numbers that are whole digits (ex: 1.0).
Pending Retirement
An article was selected for retirement by clicking Retire. It is still visible and not actually retired until the appropriate owners of the Knowledge Base it is in, approves the retirement. 
Retired
The retirement for the article was approved and it is no longer visible to users. 
Outdated
Means that a newer version of this article is available. You can check the version number of the article to see which it is. (ex: viewing version 1.0 of an article will show workflow as Outdated, when there is an updated published version 2.0)
How to view States
•	The Workflow column is visible in the back end view. Hovering over the icon displays which stage it is in. If you do not see this column you have to click on the gear icon on the top left of the list, and then add it to your Selected visible columns.

Fixing Formatting Issues
If when viewing an article any of the formatting looks off, such as a different font type, font size, or spacing issues this is typically caused by bad HTML code. More often than not it is from content that has been copied and pasted into an article without having the source formatting removed. Even if you highlight the text and manually change the font type and size to what it should be, it may still appear wrong if there is additional font styling in the code. 
You can see this by clicking the Source Code button ( <> ) in the KA editor toolbar and look for the word “style” in blue text as shown below. These inline style codes will override any other formatting for the specific text lines they are on. 
Example of bad inline style code: <span style="font-size: 12pt; font-family: 'times new roman', times;"> 
You can manually remove the entire style code, by deleting the word style and all the text formatting that appears in the reddish brown color, and leaving only the green code. 
For long articles with a lot of customized inline style codes, this can be time-consuming. To easily wipe out all style codes for an entire do the following, but note that this may cause issues if images have been pasted into an article and not inserted as an attachment. 1.	Open the source code for the article giving you issues. 
2.	Press Ctrl + A to select all of the code. 
3.	Press Ctrl + C to copy all the code. 
4.	Go to this HTML Code Cleaner. 
5.	Paste the entire code in the empty box on the right side of the screen, the left side will show a preview of what the text currently looks like.
6.	Click Clean HTML and this will remove all the inline style coding.
7.	Click Ctrl + A to select all the freshly cleaned code from the right side, and then Ctrl + C to copy it. 
8.	Go back to the source code of the KA. 
9.	Delete all existing code. 
10.	Press Ctrl + V to paste in all the cleaned up code you copied from the website. 
11.	Click OK and confirm that everything looks correct and all the previous images are still there.

1.	Highlight the text in the editor that you want to remove formatting from, or press Ctrl + A to select all the text. 
2.	Press the Clear formatting button on the toolbar, which looks like:Error! Filename not specified.
3.	This should remove any style coding from the highlighted text.

Accessibility Standards
In order to adhere to Rutgers Digital Accessibility policies, all documentation should be in compliance with Web Content Accessibility Guidelines (WCAG) 2.1 Level AA. In particular, the items below should be adhered to for all knowledge articles. 
Text Alternative for Images/Media
All images/media should have an alternative text associated with them so that screen readers can describe the context of the media. The objective of this is to create a text alternative that serves the same purpose and presents the same information as the original non-text content. 
General guidelines to follow for Alt Text:
•	You do not need to mention that it is a picture or screenshot of something, as that is implied. 
•	The Alt Text should adequately describe what is seen in the image, assuming no other context for the picture exists. 
•	If a particular button or icon is highlighted or pointed to, that should be mentioned in the Alt Text. 
•	If the image shows a series of steps, you do not need to mention the specific step numbers shown in the image since they will be in the numbered list of the knowledge article.
•	Similarly, the Alt Text should not say that it is "How to" do something, as that will be mentioned in the text of the knowledge article. 
•	Longer is not always better. Describing everything in extreme detail does not equate to good Alt Text.  
Examples
•	A picture shows the login page for Rutgers Connect. Alt Text is "Login page for Rutgers Connect prompting for an email address"
•	A picture shows how a knot is tied including arrows showing how the ropes go to make the knot. The text alternative describes how to tie the knot, not what the picture looks like.
•	A picture shows what a toy looks like from the front. The text alternative describes a front view of the toy.
How to add/edit Alt Text
For images already in an article:
1.	Click on the image to highlight it. 
2.	On the toolbar, click the Insert/edit image icon.
3.	In the Alt text field provide a short yet descriptive text alternative. 
4.	Click Save. 
Headings
In order for screen readers to appropriately describe the text on the screen to users, headings should be formatted as such. This helps users “skim" the headings to locate the specific content they need, and is especially helpful when browsers or assistive technology allow navigation from heading to heading. These heading should be short yet descriptive ways to break up long articles into smaller sections. 
All headings should be set to use Heading 2 by default. Any further separation in each section should use Heading 3 then Heading 4 etc… but should always be in increasing sequential order.
Example: An HTML page that describes the range of tasks for disaster preparation may have the following headings:

Numbered or Bulleted Lists
In order for screen readers to properly go through a series of steps or list of items it has to be formatted appropriately. A numbered or bulleted list should always be created using one of the list buttons in the editor toolbar. Simply typing numbers with parentheses or periods, such as "1), 2), 3)," or an asterisk in front of each item on a new line or paragraph will NOT create a numbered or bulleted list that is accessible by a screen reader.
A good guide to follow can be found on Microsoft’s website on the proper procedure for lists. 
Inserting images into lists
When inserting an image in a numbered or bullet sequence, press Shift+Enter to add a soft line break. This will tab down to the next line so the image can be inserted under the text, but does not continue the sequenced list for this line. After the image you can hit Enter to tab down to the next line and continue the numbered sequence. See the Images section of this article for more information on adding images.
Hyperlinks
Hyperlinks connect a hypertext file or document to another location or file. Linked information is typically presented in the form of text, websites, files, or video content. 
Embed a link within a concise string of text instead of using its URL as the link text. A screen reader user will more easily understand where an accessible link leads and will not have to listen while the reader pronounces every single character of a URL. 
Example:
•	Accessible: OIT Help Desk
•	Not accessible: https://it.rutgers.edu/help-support/
Descriptive hyperlinks will more clearly explain what information they link to. 
Example:
•	Descriptive: Benefits of Accessible Hyperlinks
•	Not descriptive: Benefits
Use the full email address as the link text rather than embedding it in other link text. 
Example:
•	Accessible: help@oit.rutgers.edu
•	Not accessible: OIT Help Desk Support *This example does not convey that it is an email address.
Other Tips:
•	Choose hyperlink text that clearly identifies the content of the resource being linked to.
•	Hyperlink text should not consist of the URL unless it is likely to be printed; e.g., Word document.
•	If a hyperlink downloads a file, be sure to mention that.
