" KB0014250 Network - Wired Network - Wired - Switches "

When using switches, you must copy the statuses of all ports involved in the changes into the ticket before making changes. Have a supervisor verify what you are doing and post approval for what you do in SN. Copy all switch work into the ticket and briefly describe what you did. One of the primary Office resources for switches is the Switchlist. This list contains information about the switches, including IP addresses, hostnames, and the rooms they serve.

Errors on the Switches

Two errors that may come up on the switches are runts and giants. Runts are discarded packets that are smaller than the average packet size. A giant is the opposite; it is a packet that exceeds the maximum packet size and is discarded. Several factors can cause runts and giants, but collisions are often the cause. If the error counters on the switch occur frequently within a short period, this could affect user connectivity and is something you should speak to a Network Support Supervisor about. 

Sometimes, a port's status may switch to "err-disabled," indicating that an error caused it to shut down. To check the cause, on an IOS switch, you can use the "show interface status err-disabled" command or "show log" to view the system log and see when it occurred and what the cause was. 

There are also occasionally issues with certain devices failing to pass their MAC addresses. This can be seen in the log, where the device shows UNKNOWN_MAC instead of its MAC address. While this can often be resolved by connecting a second device, it will resolve itself in roughly 10-20 minutes.

Switches used in the dorms

We use two switch types in ResNet Office; they are differentiated by the operating system they run. CatOS (Catalyst Operating System) is the discontinued operating system used by the older switches in the dorms. More current switches use the Cisco IOS operating system.

CatOS shows confirmation for command input and does not have a # at the end of every input line. Cisco IOS switches use different commands and do not show confirmation for command input. They are indicated by the # at the end of each input line.

Logging into the switches

Using PuTTY or Terminal (Mac), ssh to nbcs.rutgers.edu. You can then log in to the switch you want using the "telnet (switch IP)" command. Log in to the switch using your NetID and Enigma card.

Trunk ports

The trunk port of a switch receives all traffic from outside the switch and redirects traffic to the port that requested it. The trunk ports are often the first or last two ports on a blade. The port description will often list it as the trunk port. Unlike other ports, the trunk uses a gigabit fiber connection (1000Base-SX) rather than a Cat5/CAT6 connection. The VLAN can also identify it for the port, which will list "trunk".

If the trunk port is disabled, it will shut down connectivity for the entire switch and any other connected switches. If this occurs, the switch can only be returned online by NOC during regular business hours (M-F 9-5). NEVER SHUTDOWN THE TRUNK PORT.

Port security

The Port Security feature on a switch remembers the MAC address associated with the switch’s port and allows only that MAC address to communicate on that port. If any other MAC address tries to communicate through the port, port security will disable the port. ResNet uses this feature when we restrict the ports a specific user can connect to. In these cases, we will shut down the offending user's port (CIRT or rogue DHCP) and enable port security on their roommate’s port(s). This means an offender cannot access the internet from anywhere in their room. When a port security violation occurs (for example, you set port security on a port and a different MAC address tries to use that port), the port's status can revert to either "err-disabled" or "shutdown".

" KB0014255 Network - Wired Network - Wired - Switches - Frozen VLANs "

What is a frozen VLAN?

A frozen Vlan occurs when a VLAN is not included in the spanning tree of the switch. Spanning trees are based on the spanning tree protocol, which is a link layer network protocol that creates a spanning tree within a mesh network of connected switches. Links not part of the spanning tree, which leaves a single path between two network nodes, are disabled. If a VLAN does not fall in the spanning tree, the users will not receive connectivity beyond their switch.

Symptoms

Users experiencing the frozen VLAN issue cannot pull an IP address and will receive a 169.254.x.x address. However, they will show as connected on the switch and won’t be able to access websites if they are set statically. Since this issue is on our end, the user’s computer will not be the issue.

The only indication of a user experiencing a frozen VLAN is that they will show on the switch as connected but not receive Internet access. This is a good time to identify whether it is a frozen VLAN.

Identifying a frozen VLAN
Run the command: show vlan
Check the output and record the VLAN in which the problem ports are.
Run the command: show trunk ("show interfaces trunk" for IOS based switches)

If the show int trunk command does not work, see the subsection labeled "Identifying frozen VLANs on the Catalyst 3500" below.
In the output, check the section labeled "VLAN in spanning tree forwarding state and not pruned".

If the VLAN is in the list then the VLAN is not frozen. Continue troubleshooting and dispatch if necessary.

Note how all residential ports on this switch are located on VLAN 234.

Notice that VLAN 234 is included in the "Vlans in spanning tree forwarding state and not pruned" list. This means that the VLAN is not frozen.

Responsible Party (RP)

The RP can be set separately for each individual site, and for each action (grant or revoke). Privs are assigned to a position, and then the positions are in each of the different sites.

Example: if the priv is assigned to a Consultant Position at the Busch site, and a Consultant Position in the Livi site, you can set a separate RP for each. So that Busch FT are responsible for granting the priv for the Busch Consultant, and Livi FT are responsible for granting the priv for the Livi Consultant. 

Typically, it is easiest to just select all Labs/HD sites (except for Newark and Camden) and have the RP be assigned for all, even if the priv is just meant for a single site. This is done because when viewing the Privileges tab, the RP column shows you any RP assigned to that priv, and not what site each of those RPs are responsible for. Which can be confusing, and the only way to check is to go into the RP for the priv and check each individual site. This also prevents the priv from being missed in the future if the priv is assigned to a new position that is in a site that doesn't have an RP set for it (it will go unnoticed and not show up on anyone's home page to process). 

Only set the RP for a singular site if you truly want to set a specific different RP per site.

adm

If they do not have an -adm account yet, ACE will recheck every 10 minutes to try to add them to the RAD Group. On the user's Employee page in ACE, there is a section that indicates whether they have their -adm account yet (including a timestamp for when it was last checked), as well as indicating if any pending privs need an -adm account. You can also click Refresh -adm to manually run a check for their -adm account. Their adm status is updated every 10 minutes. 

Automatic Priv

These will create RAD groups that contain the NetIDs (or NetID-adm if the adm box is checked off). The name of the RAD group is listed on the Priv in the Privileges tab in ACE. The number after the "P" in the priv name is the ID number for that priv. 

Users are automatically added to the RAD group listed by ACE as soon as they are assigned a position with that privilege associated with it. They are also automatically removed from the RAD Group when they are unassigned that priv. 

Automatic privs will not have a NetID listed under "Granted by" or "Revoked By" since it was not done by an individual. 

To make a priv automatic, you must contact Anton (NetID: antsar).

Deleting a Priv

You should first check to see who the priv is still assigned to before deleting by clicking Show in the Empl. column on the Privileges tab.

A priv can be deleted by clicking the X in the Del column. It will then ask you to Confirm. If the priv is still assigned to anyone, you will get two options after clicking Confirm:

Revoke the privs right now, all at once. - This should be used if the priv does not need to still be removed from those it is assigned to. Typically, this is for a service that no longer exists and no one has access to anymore. 
Do not touch them, the privs will have to be removed one-by-one manually. - This should be used if access still needs to be removed for anyone who still has the priv assigned. A revoke action will show up on the Home page for the RP of the priv. 
Check who has a specific Priv

To see who currently has a priv, navigate to the Privileges tab and click Show in the Empl. column next to the priv you want to check. This will show you anyone who has the priv assigned (but not those who are still pending and are still on the Home list for the RP to process). 

Positions

Positions are located within a specific Site (Busch, Livingston, Newark, etc). Positions can not be moved between or copied from Site to Site. 

Adding a Position to an employee

Student Employees should only have 1 Position per Site, since each Position inherits the one below it. This also helps keep an accurate count of employees in each Position when looking at the Positions tab. 

During promotions, you should add the employee's new Position before removing their old one. 

Individually
Go to the Manage Employee tab. 
Enter their NetID and hit Enter to be brought to the employee's page. 
Click Add Position. 
Select the Site the position is in. 
Then choose the new Position to add. 
Change the start date if necessary. 
Click Confirm. 
Bulk

Follow the process for Bulk uploading new employees to add the same position to multiple employees at once. 

Removing a Position from an employee
Individually
Go to the Manage Employee tab. 
Enter their NetID and hit Enter to be brought to the employee's page. 
If they are being promoted or changing to a new Position, add that one first before removing their current one. 
Click the X next to the Position you want to remove. 
Choose the reason why and change the date if necessary.

This will show only the positions that are set to directly inherit the privs from the position you are viewing (the next step up in a sequential ladder). This does not show any subsequent positions higher up the ladder (3rd, 4th, 5th, etc.. rungs of the ladder). 

Go to the Positions tab. 
Click on the Position you want to check.

Creating a new Position

Any priv that would be specific to only select individuals, and not to an entire position, should be listed as it's own position in the Help Desk Access site. Examples of this are for individual FT that might be Admins for a service that not all FT have access to. 

Go to the Positions tab. 
Click Add Position in the appropriate Site. 
Name the Position. See the naming section below for more details. 
Click Confirm. 
You'll then be taken to the Position's page where you can assign privs and inherit positions. See sections below for more details. 
Naming

Ensure consistent name formatting with similar or sequential Positions. Copy and paste the name from similar Positions to ensure consistency. 

Inheriting privs from other Positions

You can choose if the position will inherit privs from a "Master" position or from a lower-level position. 

In the Other Positions To Inherit Privileges From box, find the position (s) you want to inherit privileges from. 
The list will show all positions on the same site first, then all other positions in alphabetical order based on the site. 
To select multiple positions, you must press CTRL when clicking on multiple positions. Clicking on just 1 position without holding CTRL will unselect any other already selected positions, and only select the one you just clicked. 
Inheriting from another position will not inherit all privs from that position. It will only inherit the privs on that position that have the Inherit checkbox marked on the priv itself in the Privileges tab. 
Click Save Changes in the Other Positions To Inherit Privileges From box when done. 
Clicking Save Changes under the Positions Info box is not the same. 
Adding Privs to a Position

If you have also just chosen to inherit privs from another Position, make sure you clicked Save Changes in the Other Positions To Inherit Privileges From box. This is so that the inherited privs are checked off accordingly (grey check marks) before you now go to check off new privs individually to the position. 

Go to the Position you want to change.
Click the heading name of each priv section to expand it. Alternatively, click Expand all sections at the top of the priv list to automatically expand all of them. 
Find the priv you want to add. 
Click the check box on the priv. If the box is already checked off and grey, that means it is already inheriting the priv from another position. 
Click Save Changes in the Position Info box to save. 
Removing Privs from a Position

This is the same as adding, but uncheck the box next to the appropriate priv. 

Note that if a priv that is not inherited is added to a position, and then the priv is changed at a later date to actually be inherited, the check box will remain blue. If you uncheck the priv box and click Save Changes, the box will now turn grey to show that it is inherited.

**NB-HD - Application Support & FT staff**

The Outage Degradation Slack channel (#esd_outage_degradation) is our primary means of communicating known outages/degradations to staff at large, including senior management and cross-campus staff.

Procedures

For all outages/degradations of service:

Once known, please post in this channel to inform staff.
As updates become available, please post additional messages.
Once resolved, please post to inform staff.
It is important to note that, once outages are resolved and users are no longer experiencing issues, we may need to re-escalate.
When posting messages in this channel, please indicate the time the item occurred, as one would do for a timeline.

For outages/degradations reported in the channel by others (outside Apps/After-hours staff):

Acknowledge the report by replying to the channel message, confirming that the matter is being looked into.
Investigate the issue; review your monitoring tools; test and verify.
If you are unable to replicate the issue, report your findings in the Slack channel and ask the original poster for more information.
If you can replicate the issue, confirm in the Slack channel and let others know you will escalate the matter.
Refer to your documentation and take the appropriate steps to escalate.
Status updates should be posted to the Slack channel as you progress through the issue, up to and including resolution times.
All posts in this channel should be noted in your event timelines and the AppSupport EOS report.
